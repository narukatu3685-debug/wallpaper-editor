# /requirements — 要件定義

## 目的

「何を作るか（What）」を確定する。技術・DB・API・画面などの「どう作るか（How）」には踏み込まず、後続工程（`/design` 以降）に委ねる。

## 開始時に行うこと

1. `docs/00-status.md` を読み、「要件定義」行の現在ステータスを確認する。
   - 既に `完了`（承認済み）であれば、作り直すのか・追加の変更として扱うのかをユーザーに確認してから進める。
2. `docs/01-requirements/questions.md` に未回答・回答待ちのラウンドが残っていないか確認する。残っていれば、まずそちらを処理する（下記「質問への回答が返ってきたとき」）。
3. `docs/00-status.md` の「要件定義」行を `進行中` に更新する。

## 初回のやり取り

ユーザーの依頼内容から要件を固めるために必要な質問を洗い出す。**チャットで質問し返さず**、`docs/01-requirements/questions.md` に「ラウンド1」として書き出す（書式・運用ルールは `CLAUDE.md` の「ユーザーへの確認は『質問シート』で行う」を参照）。最低限、次の観点を確認する。

- 誰のため・何が課題か（ユーザーストーリーの「誰が」「なぜ」）
- スコープ内／スコープ外にすること
- 優先度（Must / Should など）の判断基準

書き出したら、チャットには「`docs/01-requirements/questions.md` に質問をN件書き出しました。回答を記入したら教えてください」とだけ伝えて停止する。質問内容をチャットに全文コピーしない。

## 質問への回答が返ってきたとき

1. `questions.md` を読み直し、回答欄を確認する。他の質問の回答・既存成果物と矛盾や曖昧さがないかを必ずチェックする。矛盾・曖昧があれば、勝手に片方を採用せず新しいラウンドを追記して再度停止する。
2. 各質問のステータスを `回答済み` に更新する（ユーザーが書いた回答欄そのものは書き換えない）。
3. 未回答・曖昧な項目が残る場合は、追加質問として同じファイルに新ラウンドを追記し、再度停止する。

## 成果物の作成

1. **まず `docs/01-requirements/user-stories.md` を作成**し、チャットで提示して「このユーザーストーリーで方向性は合っているか」を確認する。
2. 方向性の合意が取れたら **`docs/01-requirements/feature-list.md` を作成**する（各機能に対応US・優先度・スコープ内外を明記）。
3. 両ファイルの末尾に承認記録欄を用意する（`ステータス: 未承認` / `承認者` / `承認日` / `備考`）。この時点では**必ず空欄のまま**にする。

## 承認

ユーザーに「このユーザーストーリーと機能一覧で、作るものの範囲として承認してよいか」を確認する。承認が得られたら、両ファイルの承認記録欄を更新する（`ステータス: 承認済み` / 承認者 / 承認日 / 備考）。この更新のみ AI が承認記録欄に書き込んでよい（`questions.md` の回答欄と異なり、ここは承認の事実を記録する場所であるため）。

## 完了時に行うこと

- `docs/00-status.md` の「要件定義」行を `完了` に更新する。
- `docs/audit.md` に追記する（質問提示時・回答反映時・承認記録時、それぞれのタイミングで都度追記する。まとめて最後に1回だけ書かない）。
- `CLAUDE.md` の「各工程の完了報告フォーマット」に従い、チャットに完了報告をする。次のアクションは「`/prototype` でデモを作り、関係者レビューに進んでください」の一択。

## 入出力

- 入力: ユーザーとの対話（`questions.md` 経由）
- 出力: `docs/01-requirements/user-stories.md`, `docs/01-requirements/feature-list.md`（いずれも承認欄つき）

# /prototype — デモ作成・レビュー

## 目的

承認済みの要件を、モックデータで動くフロントエンドのデモにして関係者に見せ、**設計・実装が始まる前に要件の漏れ・UI/UXの認識ズレを潰す**（手戻り防止）。DB・API・認証は作らない、捨てる前提のコード。

## 開始時に行うこと（ゲートチェック）

1. `docs/01-requirements/user-stories.md` と `feature-list.md` の承認記録欄が両方 `承認済み` になっているか確認する。
   - どちらか一方でも未承認なら、**着手せず**「まず `/requirements` で人間承認を得てください」と伝えて停止する。
2. `docs/00-status.md` の「デモ・レビュー」行を `進行中` に更新する。

## デモの作成

- 承認済みの `user-stories.md` / `feature-list.md` に基づき、モックデータで動くフロントエンドのデモを作る。
- 本番コードと衝突しない場所に置く（例: `src/app/prototype/` のような専用ディレクトリ、別ブランチ、別ビルドターゲットなど。プロジェクト構成に応じて判断する）。
- DB・API・認証など裏側の実装はしない。データはハードコード・モックでよい。
- `docs/02-prototype/prototype-notes.md` に、デモの構成・確認できる画面・使ったモックデータの概要を記録する。

## レビュー依頼

`CLAUDE.md` の「動作確認・起動方法」に従ってデモを起動し、確認用のURL・手順を提示して**関係者レビューを依頼し、そこで停止する**。チャット上でレビュー結果を代筆・推測しない。

## レビュー結果が返ってきたとき

1. `docs/02-prototype/review-feedback.md` に指摘を一覧化する（指摘ID `RV-01`, `RV-02`... で管理）。指摘ごとに次の2種類のどちらかに分類する。
   - **要件の漏れ・誤り** → `docs/01-requirements/` の成果物に戻して修正し、**再承認**を得る。設計・実装で辻褄を合わせない。
   - **UI/UX の指摘（操作方法・画面構成）** → その場で確定させ、`docs/02-prototype/ui-spec.md` に反映する。「後工程で決める」として先送りしない。
2. `review-feedback.md` 末尾のレビュー記録欄を埋める（実施日・参加者・要件への反映有無・`ui-spec.md` への反映有無・次工程へ進んでよいか）。**この欄はレビューの事実を記録する場所であり、AI が「レビュー済み」「進んでよい」と勝手に記入してはならない**。ユーザーから聞いた内容をそのまま記録する。

## `ui-spec.md` の作成

指摘のうちUI/UX分類のものを踏まえ、`docs/02-prototype/ui-spec.md` に画面ごとの確定仕様を書く。

- 各指摘（RV-xx）がどの節に反映されたかを表で対応付ける。
- デモでは割り切った部分（本実装で変える前提の箇所）を明記する。
- まだ決まっていない点は「未確定（後工程で決める）」として明記し、`/design` 以降が判断できるようにする。
- **この仕様は `/design`・`/implement` が必ず踏襲する。** デモのコードは捨てるが、この仕様は捨てない。

## 完了時に行うこと

- `docs/00-status.md` の「デモ・レビュー」行を更新する（レビュー待ちの間は `人間承認・レビュー待ち`、完了したら `完了`）。
- `docs/audit.md` に追記する（デモ提示時・レビュー結果反映時・完了時、それぞれのタイミングで）。
- 完了報告のフォーマットは `CLAUDE.md` を参照。次のアクションは「関係者レビューを実施してください」（レビュー待ちの間）または「`/design` に進めます」（レビュー完了後）の一択。

## 入出力

- 入力: 承認済みの要件定義
- 出力: モックで動くデモ ＋ `docs/02-prototype/prototype-notes.md`, `review-feedback.md`, `ui-spec.md`

# docs — 開発フロー成果物

各段階のカスタムコマンドが、ここに成果物を出力します。

| ディレクトリ／ファイル | 段階 | コマンド | 承認 |
|-------------|------|---------|------|
| `00-status.md` | **全工程共通。今どこにいるかの一覧** | 全コマンドが開始・完了時に更新 | - |
| `audit.md` | **全工程共通。何が起きたかの時系列ログ** | 全コマンドが追記 | - |
| `01-requirements/` | 要件定義（ユーザーストーリー・機能一覧） | `/requirements` | 人間承認 必須 ● |
| `02-prototype/` | デモの説明・関係者レビュー記録・**UI/UX 仕様**（デモ本体はプロジェクト構成に応じた場所に配置） | `/prototype` | 人間レビュー 必須 ● |
| `03-design/` | 詳細設計（DB・API・画面フロー） | `/design` | AI自走 ○ |
| `04-implementation/` | 実装メモ | `/implement` | AI自走 ○ |
| `05-acceptance/` | 受け入れテストシナリオ（出荷判定シート） | `/acceptance-test` | 人間チェック 必須 ● |

上から順に実行します。詳細はリポジトリ直下の `CLAUDE.md` を参照。

## セッションを再開するとき

久しぶりにこのプロジェクトを開いたときは、まず **`00-status.md` を読んで現在地を確認する。**
「今どの工程にいるか」「回答待ちの質問が無いか」「人間の承認・レビューが済んでいるか」が一覧でわかる。
より詳しい経緯（いつ何が起きたか）が必要なときは `audit.md` を遡る。

## デモレビューの指摘は2種類（`02-prototype/`）

`/prototype` のレビューでは、**要件の漏れ**だけでなく **UI/UX（画面構成・操作方法）の指摘**も拾います。

| 指摘の種類 | 行き先 | 例 |
|-----------|-------|-----|
| 要件の漏れ・誤り | `01-requirements/` に戻して直し、**再承認** | 「この機能が足りない」 |
| UI/UX | デモに反映し、`02-prototype/ui-spec.md` に確定仕様として記載。`/design`・`/implement` が**踏襲** | 「ドラッグ＆ドロップで動かしたい」 |

UI/UX の操作方法は、動く画面が無いと判断できないため要件定義では決めません。
**動く画面がある `/prototype` が、UI/UX を決める場所です。**「後工程で決める」と先送りしません。
デモの**コードは捨てます**が、レビューで合意した **UI/UX（`ui-spec.md`）は捨てません。**

## 質問シート（`questions.md`）

AI からの確認は **チャットではなく、各ディレクトリの `questions.md` に書き出されます。**
AI が「質問を書き出しました」と言って止まったら、そのファイルを開いて **各質問の「回答」欄に記入し**、
記入が終わったらチャットで「回答しました」と伝えてください。AI が読み直して作業を再開します。

- 質問と回答が成果物として残るので、後から「なぜこの仕様になったか」を追える
- 落ち着いて考えてから、関係者に確認してから回答できる
- 回答欄は AI が埋めません。未回答のまま先へ進むこともしません

> [!WARNING]
> **AI自走**の段階でも、コマンド承認が必要なケースはあるため完全放置は不可

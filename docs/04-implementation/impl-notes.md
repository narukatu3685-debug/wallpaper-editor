# 実装メモ

## 構成

```
壁紙処理/
├── src/wallpaper_editor/
│   ├── image_ops.py    … 画像1枚の加工処理（彩度・明るさ・コントラスト・色相・シャープネス・色温度・
│   │                      ハイライト/シャドウ・ビネット・Vibrance・Clarity・全体ぼかし・プリセットフィルター・
│   │                      反転・回転・トリミング・リサイズ）
│   ├── auto_correct.py … F-18 自動補正4パターン（画像を解析し AdjustmentSettings の一部を算出）
│   ├── batch.py         … フォルダ単位の一括処理（非破壊・失敗を許容して継続、出力形式・バッチリネーム対応）
│   ├── wallpaper.py     … Windowsデスクトップ壁紙の設定（ctypes / SystemParametersInfoW）
│   ├── settings.py      … 直近の調整値の保存・読込（%APPDATA%\WallpaperEditor\last_settings.json）
│   └── gui.py            … Tkinter GUI（エントリポイント）
├── tests/                … pytest によるユニットテスト（GUIを除く）
├── requirements.txt / requirements-dev.txt
```

起動方法: `python -m wallpaper_editor.gui`（`PYTHONPATH=src` を設定するか、`pip install -e .` 相当の配置で実行）

## 設計からの変更点（理由つき）

- `image_ops.py` の処理順序を、`api-spec.md` に書いた「彩度→色温度→明るさ→…」から **「色相→色温度→彩度→明るさ→コントラスト→ハイライト/シャドウ→シャープネス→ビネット→リサイズ」** に変更した。設計時に色相（hue）の記載漏れがあったため実装時に補い、色系の処理（色相・色温度・彩度）をまとめて先に行う順序にした。
- リサイズ方式は `api-spec.md` の設計判断どおり「中央クロップ方式」（`resize_to_fill`）で実装した。

3. 修正後の再起動で、左（対象画像一覧）・中央（プレビュー）・右（調整・リサイズ）の3カラムがすべて表示されることを確認した。

## 設計からの変更点（理由つき、2026-08-30分）

- **ハイライト/シャドウを一時的に維持**: `screen-flow.md`の設計ではF-21トーンカーブへの統合に伴い削除予定だったが、トーンカーブ自体は今回Must未実装（Should扱い）のため、置き換わる機能が無いままハイライト/シャドウを削除すると調整手段が失われてしまう。そのため今回はハイライト/シャドウのスライダーを維持し、トーンカーブ実装時に統合・削除する方針とした。
- **出力形式・バッチリネームの永続化を見送り**: `db-design.md`では`last_settings.json`に`output_format`/`rename_*`等も含める設計だったが、これらは「画像ごとの調整値」ではなく「バッチ実行時の出力設定」であり性質が異なるため、`AdjustmentSettings`（＝永続化対象）には含めず、GUI側のセッション内変数（Tkinter変数、既定値: jpg / "wallpaper_" / 1 / 3）として実装した。次回起動時は既定値に戻る。利便性はやや下がるが、影響は小さいと判断した（デフォルト値が実用上妥当なため）。
- **F-19 Before/After比較の実装方式を簡略化**: `ui-spec.md`はスライダーで比較位置を動かせる仕様だったが、Tkinterでの実装コストを抑えるため固定50/50分割表示（左=加工前、右=加工後、中央に区切り線）とした。比較自体は可能なため機能要件は満たすが、比較位置の可変化は次回検討。
- **F-15 トリミングの操作方式を簡略化**: `ui-spec.md`はドラッグで移動・角のハンドルでリサイズだったが、Tkinterでの実装コストを抑えるため「ドラッグして矩形を新規に描く」方式（再ドラッグで描き直し）とした。範囲指定という機能要件は満たす。

### 【重要】このモジュールに関する検証範囲の限界

`wallpaper_slideshow.py`の`IDesktopWallpaper` COMインターフェース呼び出し（GUID・vtableの並び順・列挙値、`IShellItemArray`の構築）は、Windows SDKの`shobjidl.h`に基づいて実装したが、**この開発環境では実機のCOM呼び出しを検証できていない**（`CLAUDE.md`「単体テスト・Claude Code の自走作業は Docker サンドボックスで行う」節の対象範囲外の、実際のWindows COM API）。

- 上記TC-56〜TC-65は、`_create_desktop_wallpaper_com()`をモックして「Python側の呼び出し引数・順序・エラーハンドリングが正しいか」のみを検証しており、**GUID値・vtableインデックス・列挙値そのものの正しさは検証していない**
- **ホスト（Windows）で`python -m wallpaper_editor.gui`を実際に起動し、スライドショーのON/OFFボタンを操作して、実際にWindowsの「設定 > 個人用設定 > 背景」がスライドショーに切り替わり、指定フォルダ・シャッフル順で動作することを手動確認する必要がある**（`CLAUDE.md`「GUI表示・実際の壁紙適用の確認はDocker（Linuxコンテナ）ではできない。ホスト（Windows）で直接実行して確認する」を参照）
- 万一GUID・vtable順が実際のSDKと異なる場合、`CoCreateInstance`や各メソッド呼び出しが`SlideshowError`（またはOS例外）で失敗する形になり、無音の誤動作にはならない設計にしている（`_hresult_check`で全HRESULTを検査）が、実機確認は別途必須

### 設計からの変更点（理由つき、2026-09-01分）

- **`slideshow_interval_minutes`の永続化を見送り**: `db-design.md`では`last_settings.json`への保存を設計したが、既存の`output_format`/`rename_*`と同じ理由（「画像ごとの調整値」ではなく「バッチ実行時の設定」であり`AdjustmentSettings`の性質と異なる）により、GUI側のセッション内変数（既定値: 30分）として実装した。次回起動時の間隔プルダウンは既定値（30分）に戻るが、ON/OFFの状態自体はWindows側から`get_slideshow_status()`で復元するため、実害は小さいと判断した。
- **`IShellItemArray`の構築方法を簡略化**: `api-spec.md`の設計では`SHParseDisplayName`＋`SHCreateShellItemArrayFromIDLists`（PIDL経由）を想定していたが、同じ結果を得られるより単純な`SHCreateItemFromParsingName`＋`SHCreateShellItemArrayFromShellItem`に変更した。
